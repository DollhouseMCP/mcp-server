## Backup before deployment — future, after deployment go

Keep automatic wrapper backups enabled. On update/rollback it copies existing `.env`/`.env.production` with mode 0600 and writes a nonempty SQL dump under `<deploy-dir>/backups/pre-remote-<action>-<UTC>.sql`; a failed required backup aborts. Those local copies are **not encrypted off-host backups**, and `pg_dump` is a snapshot, not preservation of subsequent writes.

Before the update, an operator can create the runbook's encrypted DB/secret pair as follows. Supply distinct public age recipients from the existing backup policy and a new, safe path. This command is a **future SSH/server write**, not executed during preparation. Validate path/name operands contain only safe shell-path characters before passing them as SSH arguments.

```bash

: "${DATA_BACKUP_RECIPIENT:?existing approved age public recipient}"
: "${SECRETS_BACKUP_RECIPIENT:?different approved age public recipient}"
[[ "$ALPHA_DEPLOY_DIR" =~ ^/[A-Za-z0-9_/-]+$ ]]
[[ "$ALPHA_INSTANCE" =~ ^[a-z0-9][a-z0-9_-]*$ ]]
[[ "$BACKUP_DIR" =~ ^/[A-Za-z0-9_/-]+$ ]]
[[ "$DATA_BACKUP_RECIPIENT" =~ ^age1[0-9a-z]+$ ]]
[[ "$SECRETS_BACKUP_RECIPIENT" =~ ^age1[0-9a-z]+$ ]]
test "$DATA_BACKUP_RECIPIENT" != "$SECRETS_BACKUP_RECIPIENT"
ssh -o StrictHostKeyChecking=yes -o "UserKnownHostsFile=$ALPHA_KNOWN_HOSTS_FILE" \
  dollhousemcp-alpha bash -s -- "$ALPHA_DEPLOY_DIR" "$ALPHA_INSTANCE" "$BACKUP_DIR" \
  "$DATA_BACKUP_RECIPIENT" "$SECRETS_BACKUP_RECIPIENT" <<'REMOTE'
set -euo pipefail
umask 077
D=$1; I=$2; B=$3; DATA_RECIPIENT=$4; SECRET_RECIPIENT=$5
command -v age >/dev/null
command -v gzip >/dev/null
test -d "$D" && test -r "$D/.env.production"
mkdir "$B"; chmod 0700 "$B"
cd "$D"
docker compose --project-name "$I" --env-file .env.production -f compose.yml \
  exec -T postgres pg_dump -U dollhouse dollhousemcp > "$B/database.sql"
test -s "$B/database.sql"
gzip -c "$B/database.sql" | age -r "$DATA_RECIPIENT" > "$B/database.sql.gz.age"
test -s "$B/database.sql.gz.age"
rm "$B/database.sql"
age -r "$SECRET_RECIPIENT" < .env.production > "$B/env.production.age"
test -s "$B/env.production.age"
# If filesystem portfolio/fallback state is authoritative, add a consistent,
# separately planned portfolio snapshot; do not call a live tar a no-loss backup.
REMOTE
```

## Receipt-bound rollback and beta.2 recovery limits

Rollback is **not automatic**. First close ingress through the existing reviewed maintenance control, preserve current state/new writes and take a **fresh** backup using the backup section with a new `BACKUP_DIR`. Require an operator-qualified beta.2 application versus current schema/data compatibility decision. The automation does not downgrade a database. A database restore would discard writes since that snapshot unless separately reconciled; do not restore a predeployment dump automatically. If the schema/data decision or maintenance mechanism is unknown, rollback is **blocked**, not improvised.

Use the **current reviewed beta.3 operator helper**, never the older beta.2 helper. Its rollback selects the prior source through the protected completed transition and proxy recovery receipt; a lexically newest `server.prev-*` directory does not identify that source. Before any rollback, independently inspect the exact receipt-selected source and immutable proxy identity, verify their association with the intended prior release, confirm the original volumes and protected Caddyfile, and qualify the application against the current schema and data. A missing, ambiguous or mismatched receipt blocks rollback. `recover-caddy-proxy` is proxy-only and does not restore application source or database state.

The alternative of staging beta.2 source through an update is not qualified by this plan: hold it for an explicit source, migration, schema and proxy compatibility assessment. Do not run the old beta.2 helper or infer compatibility from its tag. After an approved recovery, verify the actual running image and authenticated version before reopening ingress. Never delete volumes, reset the database, use `compose down -v`, or silently abandon postdeployment writes.
