# Local file-memory fence primitive

`FileMemoryFence.withFence()` provides bounded, cooperative exclusion for one memory locator on a local POSIX filesystem. `withTenantFence(tenantRoot, operation, options?)` takes one fixed `tenant.lock` lease under that tenant's `.memory-fences` directory, independent of any head name. Both are prerequisites for [version-checked memory writes](https://github.com/DollhouseMCP/mcp-server/issues/2870), not persistence or archive stores. No memory writer uses either primitive yet. Mixing per-memory and tenant-wide leases does not serialize those writers. Lost updates remain possible until every file-memory writer, including entry, clear, metadata, rollover, and erasure paths, participates in one scope and checks the durable head version under it. The database backend needs its own transactional version check.

The caller supplies a tenant root, canonicalized with `realpath`. For `withFence`, the caller also supplies a relative memory locator. Its existing components are checked with `lstat`, rejecting symlinks and hard-linked target files. A restricted lowercase ASCII locator namespace prevents unresolved case and Unicode aliases from getting different lock keys before the file exists. Dot aliases normalize to the same key. The lease name hashes the relative locator within the tenant root's own `.memory-fences` directory, so two local bind-mount aliases of that same directory converge without depending on their absolute paths.

The tenant-wide API has **no memory locator** and does not apply the lowercase ASCII restriction. A future file-store integration can therefore lock before handling a valid legacy head such as `Legacy/RÉSUMÉ.yaml` or `Legacy/日本語.yaml` without renaming it on read. All cooperating head/archive create, claim, write, rename, delete, and erasure paths must take this same tenant lease first. This sacrifices parallel writes to different memories in a tenant; acquisition timeouts and throughput need qualification. The lease does **not** validate the actual head path: callers must separately enforce tenant confinement and their symlink/hard-link mutation policy while holding the lease. It does not by itself solve raw-path aliasing, durable ownership, or conditional head writes. The tenant root and its ancestors must be trusted against concurrent filesystem replacement. Both APIs are deliberately unsupported on Windows and do not claim safety across independent mount namespaces, network filesystems, or hosts with different `mkdir` or cache semantics.

`FileMemoryTransactionCoordinator` is an unwired composition layer over the tenant fence. Construct it for one tenant/request from a root and user resolver captured from the same active context; do not store one startup-root coordinator in the root `MemoryManager` singleton while its `memoriesDir` varies by user. A coordinator-backed `FileMemoryOwnerSnapshots` shares that exact coordinator with future head and archive stores. Standalone snapshot reads still acquire no lease and write nothing. In a transaction, audited store methods use the coordinator's opaque context, captured canonical root and user, and one fence acquisition. The coordinator runs accepted store operations in FIFO order, drains them before releasing the lease even if the caller omitted an operation `await`, and rejects queued work after a failure. It rejects nested **coordinator** transactions and tracked store operations to avoid non-reentrant locking or hidden cycles. An expired context cannot start more work. This lifetime guarantee covers operations routed through audited store APIs whose own I/O is awaited; arbitrary detached filesystem work is outside it. Direct calls to the raw fence or a separate legacy-mode owner store inside the callback bypass this guard and can self-wait; production integration must use coordinator-bound audited stores exclusively.

Each tracked `perform` call also receives a private operation scope. It is valid only in the async flow of that issuing operation and expires when the operation settles, even if the outer transaction still holds its fence. Work already accepted by the FIFO queue may run while the outer callback is closing; its scope remains valid until that work settles and the queue drains. `FileMemoryOwnerSnapshots.requireOwnedAtScope` rechecks an expected ACTIVE owner token against the head, sidecar, registry and write-journal guards within that same operation; an archive store must **await** this helper before publishing data. A structural read scope or an operation scope borrowed from another flow cannot authorize publication, and the helper acquires no second fence. These checks provide ownership/exclusion evidence, not rollback of an earlier committed operation or tracking for detached raw filesystem I/O.

The transaction layer provides **exclusion and lifetime**, not rollback or an atomic multi-step commit. Adoption can already commit an ACTIVE owner sidecar before a later operation fails; the caller must report that failure without claiming the adoption was undone. The file head write/rename/delete journal, archive receipt cleanup, tombstone erasure, all-writer routing, and recovery state machine remain separate prerequisites in [#2870](https://github.com/DollhouseMCP/mcp-server/issues/2870) and [#2871](https://github.com/DollhouseMCP/mcp-server/issues/2871). No production writer uses the coordinator yet.

An exclusive `mkdir` creates a private `0700` lease directory under `.memory-fences`; a random-token `0600` owner file is written and synced. Acquisition has a finite timeout. Release checks the directory device/inode and owner token before removing only that lease. A handled callback failure releases its lease; if release also fails, both errors are reported. A process crash leaves the directory in place, including a crash before owner-file creation. Neither age nor PID authorizes automatic stealing.

For a crashed lease, stop **all** writers for that tenant storage first. Confirm that no process can still own or acquire the fence, inspect the specific `.memory-fences/<hash>.lock` or `.memory-fences/tenant.lock` directory and any owner file, then remove only that lease directory and restart writers. Never remove a lease while writers run: inode/token checks cannot make an operator-initiated unlink and recreation safe against ABA races. Missing owner metadata is a reason to investigate, not evidence that the lease is free. This procedure covers process crashes; power-loss durability and multi-host coordination require separate validation before deployment.
