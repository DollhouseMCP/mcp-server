# Dormant database memory admission gate

This is unit 1 of the DB-first plan in [#2870](https://github.com/DollhouseMCP/mcp-server/issues/2870), governed by [#2998](https://github.com/DollhouseMCP/mcp-server/issues/2998). Production composition remains unchanged: adding this code and an empty mode relation does not enable guarded storage or qualify a head.

The initial binary recognizes only protocol 1, backend `database`, profile `existing-owner-archive-free-update-v1`, and mode `guarded`. Durable `read_only`, missing records/config/adapters, unknown protocol/profile, stale generations and context drift refuse admission. There is no legacy state or automatic seed/adoption/promotion in this boundary.

A trusted server callback supplies the authenticated database tenant and actual database/store/adapter references before awaits. Readonly identity checks also verify the effective store/adapter tenant. Private WeakMap captures are instance-specific; copying a response-shaped object, restarting the gate or presenting a capture from another gate conveys no authority. No request field selects a backend or profile.

`withAdmission` starts a tenant-scoped transaction on the captured database, rereads and locks the durable mode `FOR SHARE`, then verifies generation and trusted binding before dispatch. The callback receives that exact transaction. The row lock serializes durable mode transitions through transaction completion. JS config/context checks occur at documented synchronous boundaries; they are not an atomic lock on arbitrary config changes through COMMIT. Later writer integration must use this transaction for its conditional persistence; an admission preflight followed by today's independent head-write transaction is not compliant.

Independent callbacks may hold compatible share locks concurrently. This gate is not a tenant-wide callback mutex: runtime callbacks cannot change the mode row or generation, and privileged mode updates wait for the admitted transactions to complete. Per-head conditional revision/ownership enforcement belongs to the later writer integration, not this mode-stability lock.

The new mode relation has ENABLE/FORCE RLS and tenant SELECT visibility. PostgreSQL applies UPDATE USING policies to row-locking SELECTs, so a tenant UPDATE USING policy exists with WITH CHECK(false). Actual updates, including no-op updates, remain forbidden. Operational setup requires only SELECT and UPDATE(generation) for the ordinary non-BYPASS runtime role; the migration does not grant PUBLIC access or choose a production role. No INSERT/DELETE policy exists. A trigger prevents key changes/deletion and advances generation on every update without wraparound. Mode writing is privileged operational work, outside this implementation's runtime API.

Known precommit rejection rolls back the callback transaction when rollback completion is known. Commit/rollback transport errors preserve their original causes and remain outcome-unknown; there is no safe-replay or unconditional no-mutation claim. Best-effort redacted failure observation follows failed transaction/cleanup, contains observer failures and exposes no tenant, raw content, owner token or error message. It establishes neither guaranteed nor crash-durable delivery.

The mode record cannot constrain an old binary or privileged DDL. Before enabling any cohort, the remaining units must qualify complete route-or-refuse coverage, actual old-writer/queue/access exclusion, fresh owner/raw/projection/archive-free eligibility, supported capacity, candidate/outcome restart semantics, read-side effects, backups/restore and compatible guarded/read-only rollback. Global maintenance qualification is not replaced by a tenant mode record. #2998/#2906/#2907 remain open; no live maintenance, activation or deployment is authorized by this dormant slice.
