# Authentication methods for invited accounts

Users created through durable invitations require a coherent GitHub identity for normal authentication. The retained `account_invitations.user_id` relationship identifies this cohort, independent of invitation state. Issuance creates a new user and its invitation atomically; it does not enroll an existing legacy user into the cohort. Deletion retains the anonymized relationship. Removing retained invitation history in a future migration must preserve this policy marker.

No schema flag, legacy migration, or email matching is introduced. Existing active users without this marker, including local administrators and service accounts, keep their existing methods. Pending, disabled and deleted checks remain independent. A cohort identity must have persisted provider `github`, a positive numeric external subject, and subject exactly `github_<external subject>`; changing a provided provider string or renaming an inconsistent stored subject cannot upgrade it.

The normal AS/token eligibility check, console resolver and authenticated MCP identity resolver reject previously linked alternative methods. Authoritative credential upserts and identity attachment reject new alternatives too. This covers local invite/password credential replacement and magic-link redemption, which use the shared upsert. Unrelated identities sharing an email remain separate accounts. There is no implemented password-reset consumer to wire separately.

Policy reads run inside the existing privileged system context and propagate database failures. Identity attachment takes the target users row before the auth row; credential upsert takes a nonblocking users table read lock that conflicts with issuance, then checks the canonical link/username fallback and repeats its predicate against the conflict row while PostgreSQL owns that row. The conflict predicate validates both existing and incoming identity coherence. Issuance rejects an existing auth subject with the proposed username, so whichever writer wins preserves its account boundary. Contention aborts the entire caller transaction without automatic retries. These narrow checks preserve the existing mutation resource preflight; they add no broader table locks. No route or provider is registered by this slice.
