# Dormant guarded console memory updates

Issue [#2995](https://github.com/DollhouseMCP/mcp-server/issues/2995) integrates existing-owner console MEMORY UPDATE with the dormant manager adapter. Production selection remains unchanged. Guarded CREATE and DELETE refuse; legacy console routes retain their behavior.

The console reads a fresh inventory of current names, collects every canonical-name or filename-stem match, and requires one locator. It then reads and hydrates that exact owned snapshot. Guarded memory detail ETags hash the complete captured raw UTF-8 snapshot, including auxiliary state; editable GET content remains a separate projection. Responses hash the exact prepared serialization before dispatch. Ordinary, legacy and uncaptured list projections retain their existing ETag algorithm. Cached/list content never receives a refreshed token. Name discovery is not a global atomic namespace snapshot. The backend conditional write fences the selected owner.

`MemoryManager.findGuardedMemoryForUpdate` returns the snapshot content, locator and privately bound working memory. The console-specific working object preserves a present nonempty string `unique_id` from those same bytes. When the persisted field is absent, preparation and first-save serialization consistently use that captured object's existing constructor ID; the original raw ETag remains unchanged until the conditional write commits. No UUID restriction is added to this metadata field; backend owner authority remains the full private token.

`prepareGuardedMemoryReplacement` derives a quiet candidate synchronously before parsing or validation awaits. The replacement preserves the source's name, persisted identity, original authority and unknown lineage. It rebuilds runtime configuration consistently, preserves omitted instructions/extensions and accepts structured entries including an explicit empty array. Unsupported plain-text replacement and rename refuse. The source's content and token remain unchanged; a later stale source write cannot erase the replacement.

Replacement runtime configuration uses the normal manager parser's existing precedence for `storage_backend`, `privacy_level` and `retention_policy.default`. Their effective canonical fields agree in the submitted serialization and committed runtime object. Unknown metadata and the raw legacy fields remain preserved.

The store reserves an authenticated/effective-tenant request key before lookup and an exact locator key before preparation. Missing targets, invalid preparation and failed ETags release reservations before dispatch. Refused backend attempts, unknown outcomes and known-commit publication failures retain candidate, manager and original cause in process-local diagnostics. An alias cannot overwrite retained target evidence. There is no automatic retry, crash-durable caller ledger or public token getter.

The response and `updatedAt` come from the submitted candidate serialization, prepared before save. They are returned only after save succeeds and context is rechecked. A subsequent writer's GET is never substituted for this operation's response. Backend stale conflicts map to the existing console version-conflict error while diagnostics preserve the original backend cause. Unknown and known-commit failures are not flattened into a precondition failure. Network delivery durability is not promised.

Local qualification covers the actual file store, a separate-process competing writer, nested entry metadata, complete auxiliary state, runtime capacity, explicit empty entries, ambiguous names, exact root/system locators, context drift, preparation release, unknown replay refusal and genuine committed publication failure. Six isolated PostgreSQL cases are authored for required CI; local PostgreSQL execution is not part of qualification. The broader all-writer route-or-refuse activation gate remains open.

Guarded replacement validates authored control fields and gatekeeper policy before load-time normalization. Present description, tags, triggers and gatekeeper fields use the established loader values; absent fields remain absent. Effective raw tags retain the console validation and precedence rules, then loader-canonical tags are checked with the same validator before dispatch. For example, accepted `a;b` becomes `ab`, while a tag that becomes empty refuses without a write. This keeps committed runtime metadata consistent with a normal reload.

Console discovery also uses the established loader name normalization, counting all raw, normalized and nonempty filename-stem candidates before accepting one locator. A captured nonempty legacy raw name remains immutable persistence identity while runtime identity stays normalized. Private source evidence has no serialization effect: only a console replacement candidate and its detached persistence copy preserve that raw spelling. Public loads, generic mutation derivation and published/cache objects retain existing serialization behavior. File lookup checks exact raw summary/snapshot agreement; database row/token/runtime equality remains strict.

An unrelated raw-unmatched summary whose name fails the existing normalizer is excluded only as a discovery hint. Raw matching malformed targets still undergo strict hydration/refusal, and every genuine matching candidate still counts toward ambiguity; unexpected validation errors propagate. Replacement preparation requires finite constructor-effective entry and retention limits before the JSON persistence roundtrip, keeping existing valid/default/clamp behavior and preventing nonnumeric limits from bypassing runtime bounds.

Numeric retention strings retain the loader's existing representation and expiry behavior; finiteness checks use the existing numeric interpretation only. This does not introduce a new retention or expiry policy.

After admission, a guarded save with a recorded `refused` outcome invokes the existing `MemoryManager.onSaveError` hook once. Hook/listener failure cannot replace the original refusal or pending receipt. Unknown outcomes and known-commit publication failures are not labeled failed saves. Pre-admission refusals and other writer paths retain their existing behavior. This hook uses the existing in-memory security monitor and log forwarding, with its deduplication, current-context attribution and existing detail/redaction limitations; it does not prove crash-durable audit delivery or complete refusal coverage.

The shared namespace-refusal audit prerequisite in [the adapter contract](memory-head-update-adapter.md) remains open before file-writer activation, alongside issues [#254](https://github.com/DollhouseMCP/mcp-server/issues/254) and [#2789](https://github.com/DollhouseMCP/mcp-server/issues/2789). Production selection remains unchanged. The bounded hook correction does not resolve pre-admission, generic unknown, postcommit or DELETE/RENAME logging gaps.
