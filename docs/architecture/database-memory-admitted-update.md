# Dormant admitted database UPDATE seam

This is scheduling unit 2A under #2906/#2998 and the six-unit plan in #2870. Production DI remains unchanged. It supplies the transaction prerequisite for foreground routing; it does not route those callers, qualify owner eligibility or enable a cohort.

The optional trusted `MemoryHeadUpdateAdapter` admission resolver binds a private gate capture to the original loaded snapshot and its derived candidates. Missing private authority or a changed gate refuses; an admitted adapter never falls back to the independent conditional writer. Existing two-argument adapters and ordinary storage operations retain their existing behavior.

`DatabaseMemoryAdmissionGate.withAdmittedWrite` uses the protected transaction and durable mode row lock. Its write authority is a private invocation-specific capability bound to the actual transaction, store and tenant. Structural copies, another store/tenant and use outside the callback or after uncertain outer completion refuse. A late callback cannot mint authority after its enclosing invocation has already failed. `prepareHeadWriteInAdmission` accepts that capability rather than an arbitrary transaction. It shares the existing conditional SQL and parent/tag/child synchronization, and supports only unchanged-name UPDATE. Its receipt/token is prospective. No index or success audit publishes during preparation.

Only after the enclosing transaction reports success does the gate mark private committed authority, and only then does the adapter advance its token and invoke publication. A prepared receipt cannot publish before commit or after rollback, even if it escapes the callback. Publication is one attempt; a failure after known commit retains the attempted candidate and committed token as `committed-publication-failed`. It does not claim rollback.

For the supported Drizzle/postgres.js driver, a protected callback failure is wrapped in a unique private sentinel. The driver awaits ROLLBACK before rethrowing that exact identity. Only that returned sentinel supplies a known rollback/refusal descriptor; the original cause is unwrapped without replacing null, undefined or reused error objects. Different BEGIN/context setup, connection-close, rollback or COMMIT errors remain `unknown`, even with a familiar refusal code. A successful callback followed by failed completion never advances the token or publishes success. Pending unknown state retains the original token and attempted bytes and prevents further writes on its related lineage. No automatic replay or durable candidate/restart guarantee is introduced.

Focused tests cover controlled completion and observer boundaries. The required PostgreSQL suite exercises actual parent/tag/child rollback, known commit/final revision, wrong-store/tenant and context refusal, mode-transition exclusion, escaped receipt refusal, actual commit followed by injected completion-delivery failure, and local publication failure. The completion-delivery injection is not a claim to reproduce a provider network fault. Actual hosted execution and owned fixture cleanup are required for qualification; local mocks or skips are insufficient.

Foreground unit 2 and deferred/admin unit 3 remain separate. Fresh eligibility/global maintenance, read effects, durable outcomes/candidates, old-writer access exclusion, compatible rollback, production composition and operational #2907 admission remain open. This seam does not constrain old binaries, direct legacy writers or privileged DDL, and authorizes no migration, deployment or activation.
