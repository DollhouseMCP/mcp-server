# Invitation writer conflict protocol

The durable invitation management store and legacy console invitation issuer reject a new account when its username or recipient email matches an existing `users` row. Neither writer links to that account or merges identities by email. Stored usernames use NFC, trimming, lowercase, then NFC, matching the shared account-name canonical spelling without imposing newer syntax rules on historical rows. Recipient email comparison uses the existing `normalizeAuthAllowlistValue('email', ...)` policy (NFC, trimming, lowercase). Legacy stored spelling and token contents remain unchanged.

Both invitation writers acquire `users EXCLUSIVE` before reading conflicts and retain the lock through account creation and commit. This prevents the second writer from relying on a snapshot taken before the first writer commits. The legacy writer uses the existing `lockAuthMutationResourcesWithTx` preflight: after users, downstream auth, role, allowlist, audit and invalidation resources are locked with `NOWAIT`. A writer that already holds a downstream resource and is about to check a users foreign key therefore cannot form a blocking cycle. Contention rolls the entire transaction back and produces a sanitized console conflict; the operation does not automatically retry. The legacy console service writes its audit in a subsequent transaction, after the issuer releases these locks. Durable administrator mutation audit remains in its existing transaction with its existing audit-head safeguard.

This closes the two participating invitation writers' reverse-order duplicate gap in #2697. It is not a global email uniqueness constraint. Existing collisions are preserved, and ordinary authentication never acquires email-based identity ownership from this policy. Account deletion retains its users-row-first protocol; its `ROW SHARE` lock conflicts with the invitation table lock before either path accesses downstream identity records.

The current creation inventory also includes `UserIdentityService` (ordinary canonical user provisioning and local identity creation), `PostgresConsoleIdentityResolver.linkAccount`, `provisionConsoleAdmin`, database bootstrap, and `SystemUserProvisioner`. These create usernames and optional display names without writing recipient email. Ordinary `PostgresAuthStorageLayer` upserts provider email metadata in `auth_accounts`, not `users.email`. Console profile updates change display names; deletion clears identity fields. No application import writer was found in the current `src`/`scripts` inventory. Direct database writes and future import/email-update paths are outside this protocol.

The remaining #2697 work stays open: explicitly reconcile pre-existing collisions, establish policy for all user writers, and replace the broad lock/full scan only after measuring contention and proving equivalent concurrency behavior. This change adds no migration, route, deployment, or automatic retry.

PostgreSQL regressions run both actual invitation writers with each transaction paused immediately before commit, observe the second writer blocked on users, then verify one canonical email owner and no partial losing account/identity/role/invitation/audit writes. Separate downstream auth, role, and audit-head contention tests verify immediate rollback and a later explicit retry.
