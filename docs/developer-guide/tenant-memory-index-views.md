# Selected database memory index views (C1)

This dormant caller seam binds PortfolioIndex, EnhancedIndex and optional UnifiedIndex to one authentic `TenantMemoryOperationProvider` operation. It installs no production provider and grants no boot qualification or storage activation authority. C2 must wire the actual authenticated routes and concrete whole-tenant qualifier; the final authenticated, distinct-session and compiled-process restart proof remains separate.

The factory derives its namespace from the already captured registry tenant, validates it against the actual PortfolioManager directories, and retains the original operation through every index read. It never selects a tenant from an index path or replaces a manager after an await. Each view owns its local index/result caches, NLP corpus and relationship graph. Remote collaborators retain their existing ownership; structurally supplied cache properties cannot replace the view-owned caches.

Memory discovery branches to the selected database manager **before** filesystem existence checks. The explicit `strictDatabase` listing option propagates scan, summary, effective-owner and individual-load failures; omitted ordinary listing keeps its existing best-effort behavior. A bound local failure cannot become an authoritative empty/partial index, remote fallback result or zero duplicate count. Memory index entries use the persisted UUID as their locator and the hydrated logical name as their filename hint; consumers must use the selected database manager rather than treating that UUID as a filesystem path.

Guarded EnhancedIndex derivation stays in RAM across load/build, lock acquisition, relationships/extensions, action metrics, explicit flush/cleanup and disposal. It creates no derived index file or lock file, does not stat/load an old disk index, and schedules no filesystem-writing metrics/telemetry callbacks. Explicit `persist()` refuses. Ordinary construction keeps its existing file behavior; an explicit LEGACY bound view still writes the captured tenant's index file and requires the ordinarily initialized portfolio directory. Invocation-bound views do not start periodic cleanup callbacks; ordinary PathService construction retains them. Views must still be disposed to release their owned NLP/metrics resources. This does not change authoritative memory heads or implement archive mutation.

Original binding checks cover public result boundaries and the actual awaited algorithms. The RelationshipManager path/connected-element algorithms are synchronous; their result checks and injected closure tests are defensive coverage, not proof of a newly discovered asynchronous relationship race. The cached EnhancedIndex accessor already rechecked through `indexPath`; its explicit final check makes that boundary visible.

The tests cover RAM-only public methods, real ordinary/LEGACY file persistence, strict errors versus ordinary empty-list compatibility, normal/streaming fallback, view-owned cache isolation and original-context refusal. The required PostgreSQL case is authored to exercise actual selected tenant discovery, UUID load/serialization and activation, two tenant views, complete head/projection snapshots and absence of index/filesystem writes. Local PostgreSQL execution is skipped when the required hosted service is unavailable; authored assertions are not executed evidence.

This slice does not establish arbitrary legacy-data fidelity: existing hydration validation, quarantine and sanitization remain. The separate #3018 guarded load-retention suppression is required before the complete guarded read profile can activate. Dirty=false alone is not owner/raw/child/archive/policy eligibility. Production composition must also enforce trusted HTTP identity, candidate/quota and closed-boot requirements, supported capacity, account/admin/deferred writer refusal, and cold exclusion of every old process/request/queue. Index view disposal does not prove those operational drains.
