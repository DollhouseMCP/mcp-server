# Private tenant memory composition and startup admission

This is the first implementation slice of [#2998](https://github.com/DollhouseMCP/mcp-server/issues/2998#issuecomment-6053805562). It provides private tenant entries and a startup refusal boundary. It does not install the registry in production, qualify data, enable guarded storage, or replace the existing HTTP handler wiring.

The server captures its trusted effective database tenant synchronously, installs one initialization flight for that tenant, awaits that exact flight, rechecks the effective tenant, and returns one actual manager. Concurrent sessions for the same tenant share the entry; different tenants have separate managers, factories and boot controllers. UUID validation is not authorization. Capture checks tenant identity, not complete request/session attribution; the subsequent async handler wiring must preserve invocation attribution separately.

Entry kind is immutable and selected only from an explicit durable mode tuple. `legacy-memory-writes-v1` creates an ordinary manager backed by the mode-enforcing factory. `existing-owner-archive-free-update-v1` creates the durable admitted composition with a closed boot controller. A `read_only` row remains protected and its admission gate refuses mutations. Missing, malformed or unsupported state, failed initialization, and context drift refuse rather than selecting legacy persistence. No in-process promotion, replacement or automatic retry is provided. Qualification shares an in-flight attempt; a terminal attempt cannot be reused as fresh qualification.

The database registrar always checks startup admission, including when no registry is configured. It compares the actual application connection with the authoritative system connection using server address/port, postmaster start time and database name/OID. Unknown endpoints (including connections without a concrete IP/port), mismatched databases, unavailable expected schema, corrupt tuples and protected rows without matching trusted composition refuse startup. The system identity, catalog and whole-database mode observation share one read-only system transaction. The application identity is observed through its actual connection. This is a bounded startup observation, not proof of complete DDL, grants, data eligibility or exclusion of a later hot transition.

The registry exposes no request-selected mode, automatically provisioned legacy row or eviction API. Closing it denies new access and closes ready boot controllers; it does not cancel or drain in-flight work, dispose retained managers, delete candidates or prove shutdown. Failure observations are redacted and best effort; observer errors preserve the original refusal. They do not guarantee durable audit delivery.

Before any activation, separately qualify the actual async HTTP/AQL/console/activation wiring, authorized target context, all reachable writers and derived read side effects, whole-cohort eligibility, candidate quota and closed restart behavior. Cold promotion must exclude old binaries and all replica request/admin/account/queue writers. Startup observation does not establish that exclusion. Existing capacity, oversized recovery (JavaScript string-unit bounds), two authenticated session CAS, fresh-connection/restart and rollback proofs remain required. No archive, POSIX or operator UI feature is added by this slice.

Local controls exercise the actual registrar's config-off refusal, manager identity isolation, terminal boot qualification and unknown database identity. The required PostgreSQL suite additionally checks foreign protected rows, real mismatched databases, nullable malformed catalog state and actual tenant-bound manager isolation, with unchanged head snapshots. Authored PostgreSQL tests are not execution evidence; hosted assertions and cleanup must complete on the published head.
