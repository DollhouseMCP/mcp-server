# Hosted Connect client qualification matrix — 2026-09-26

This is an evidence ledger for the **40 exact client surfaces** shown in the beta Connect catalog (7 core, 4 native handoff, 29 additional). A displayed guide or generated link is not a successful installation. Columns deliberately separate the advertised Connect route, browser-to-app handoff, saved client configuration, Dollhouse OAuth, and a harmless real Dollhouse MCP tool call. Tool discovery alone does not satisfy the last column. The [additional guide source list](hosted-additional-client-guides.md) and [install discovery](https://github.com/DollhouseMCP/mcp-server/issues/2809) provide first-party route links; the issue column tracks remaining acceptance.

**Legend:** `D` = documented route or source-confirmed link, not executed; `T` = observed in this run on macOS 26.5.2 (arm64), with detail below; `H` = earlier project evidence, not repeated in this run; `—` = unverified; `N` = no direct custom hosted MCP route established. `Blocked` names an access or platform prerequisite, not a failed product. No row below claims complete end-to-end qualification.

## Direct observations and limits

- **Claude Code 2.1.273, macOS arm64:** `claude mcp add --help` advertises HTTP, `--scope`, OAuth client options and callback port; `claude mcp login --help` advertises `--no-browser`. With a task-only `CLAUDE_CONFIG_DIR`, `claude mcp add --scope user --transport http dollhouse-qual https://example.invalid/mcp` exited 0 and wrote `mcpServers.dollhouse-qual = {"type":"http","url":"https://example.invalid/mcp"}` to that isolated `.claude.json`. A second add retained both names. Removing the first with `claude mcp remove --scope user dollhouse-qual` retained the second. The invalid example endpoint prevents a claim about Dollhouse network reachability, OAuth, session hot loading, or tool calls. No existing user config was edited.
- **Codex CLI 0.158.0-alpha.2.1:** `codex mcp add --help` advertises `--url` for Streamable HTTP plus OAuth registration modes; `codex mcp login --help` advertises `--no-browser`. A read-only `-c 'mcp_servers.dollhouse_qual.url="https://example.invalid/mcp"'` overlay appeared in `mcp list`. This validates parsing, not persistence. `mcp add` was not run against the real global config.
- **Installed app versions:** ChatGPT 1.2026.118, Claude 2.9939.1, Codex 26.924.22138, Cursor 3.6.21, VS Code 1.122.1, and Windsurf 2.3.15 were read from the app bundles without opening them. The VS Code and Windsurf command-line launchers report 1.122.1 and 1.110.1 respectively. Both CLI help screens expose `--add-mcp <json>`. That is syntax evidence only; the command writes a user profile and was not run. VS Code's prior project record reported OAuth and tool discovery, not a tool invocation.
- **Local app installers:** [Hermes official Mac download](https://hermes-agent.nousresearch.com/desktop) supplied a 6,752,854-byte signed/notarized DMG. Its `Hermes-Setup` bootstrap installed Hermes Desktop/CLI v0.21.5+2990; the resulting `~/.hermes` uses 3.6 GiB. [LM Studio's official Mac arm64 route](https://lmstudio.ai/download/latest/darwin/arm64) supplied a 569,866,427-byte signed/notarized DMG; LM Studio 0.4.25+1 is installed. Both DMGs passed checksum, `codesign --verify --deep --strict`, and Gatekeeper assessment. No model was downloaded. After Hermes bootstrap, disk free space was 149 GiB, above the 140 GiB reserve.
- **LM Studio live handoff:** A Safari click on the Connect `lmstudio://add_mcp` link opened an Add MCP Server dialog with the intended named HTTPS endpoint. Saving added the integration to a blank chat and its toggle worked. Read-only inspection found the new `~/.lmstudio/mcp.json` entry and an `mcpBridge` plug-in with the same URL; the entry contained only `url`. The available main log had no matching connection/authentication event. No model was installed, no OAuth prompt appeared, and no tool was invoked. It remains unknown whether using a model or another action triggers the first server connection.
- **Claude Desktop live UI and call:** In version 2.9939.1 the route is Customize → Connectors → Add connector → Add custom connector, then a Name/MCP server URL form and Continue. A duplicate URL was rejected because an organization connector for the exact Dollhouse endpoint already existed. Under Yours → Dollhouse Alpha Test, the existing connector showed Expired; Reconnect opened Safari's Claude handoff and Dollhouse OAuth consent for `mcp` and `offline_access`. The user approved; OAuth returned success to Claude. The connector then enumerated 10 tools. In a new bounded smoke-test chat, the actual tool panel showed hosted `mcp_aql_read` called with `{operation:"introspect",params:{query:"operations"}}` and returned the operation catalog JSON, request `1790461151552-74216560` at 2026-09-26 22:19:11 UTC. A fresh duplicate server was not saved. The Connect guide should direct users to reconnect an existing matching URL before trying to add another entry.
- **ChatGPT web setup:** In a signed-in ChatGPT account, `chatgpt.com/plugins` → Add → Create MCP App displayed Name, optional Description, Connection Server URL/Tunnel, OAuth authentication (default), a trust acknowledgement and Create. Continuing to the created app opened Dollhouse consent for `openid`, `email` and `mcp`, with a ChatGPT callback. User approval and tool access remain pending. The [current first-party setup guide](https://developers.openai.com/plugins/deploy/connect-chatgpt) places developer mode under Settings → Security and login; this account already exposed Create MCP App, so no settings toggle was tested.
- **Codex desktop limitation:** The installed desktop UI could not be automated because macOS safety access denied the computer-use process. No workaround was attempted. CLI syntax and read-only overlay evidence above do not qualify the desktop add-server UI.
- **Cursor native handoff:** Safari accepted the generated `cursor://anysphere.cursor-deeplink/mcp/install` link and opened Cursor 3.6.21, but the app remained on Login/Sign Up. No import dialog, saved config, OAuth prompt, or tool call was observed; login is the present qualification blocker.
- **Hermes Desktop and CLI:** In v0.21.5+2990, Capabilities → Connectors → Add your own accepted a name, Streamable HTTP URL and Auth OAuth, then saved `mcpServers.dollhouse-qual-hermes` with `url` and `auth: oauth`. Desktop initially showed “The server refused the connection” and no tools. Narrowed local logs explain this test as `OAuthNonInteractiveError`: no cached token was available in the non-interactive Desktop path, and they direct an interactive `hermes mcp login <name>` first; no HTTP 401/403 appeared in those logs. The user approved the browser PKCE consent reached by that official CLI login, which exited 0 as authenticated. `hermes mcp test dollhouse-qual-hermes` then exited 0, connected in 2123 ms and discovered 10 tools, including `mcp_aql_read`. After More actions → Refresh tools, Desktop showed the connector On and listed the same 10 tools. Its CLI exposes no native specific-tool invocation subcommand, and expanding a tool in Desktop showed only its description, so this is OAuth plus discovery, not a real tool-call pass.
- **Other CLI candidates:** First-party installation pages name `@google/gemini-cli`, `@github/copilot`, and `opencode-ai`. A proposed task-only npm install with lifecycle scripts disabled was blocked by the local PreToolUse policy (`Dangerous command pattern: npm install *`). No alternate install route was attempted to bypass that rejection, so those three clients remain untested.

The next live-client pass must record exact version/OS/browser, endpoint and test account type, whether the browser handoff actually opened an import/consent UI, whether the server persisted alongside existing entries, whether an already-open session picked it up, OAuth cancellation/retry, tool discovery, a harmless tool invocation, removal, and whether local hook/enforcement support exists separately. Account, tenant, OS and subscription blockers stay explicit rather than becoming a pass. No test here invoked a paid model or granted OAuth.
