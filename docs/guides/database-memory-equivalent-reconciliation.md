# Dormant equivalent database reconciliation

Ordinary database writers can leave a legacy head dirty. This internal candidate qualifies only an archive-free head whose raw YAML, indexed metadata, complete children and tags are already equivalent. It preserves raw content and accepted structured data. Divergent repair, archive support, all-writer routing and activation remain separate work under #2905, #2906 and #2907. Nothing wires this API into production or authorizes an operator run.

`DatabaseMemoryEquivalentReconciler` takes an ordinary database, authenticated user resolver, separately privileged root postgres-js connection and explicitly configured ordinary application-role name. `prepareEquivalent(owner)` returns diagnostic inspection plus a frozen comparison proposal when eligible. Neither the proposal nor the ordinary inspector report grants maintenance authority.

`qualifyEquivalent(proposal, currentMaintenanceRequest)` uses one reserved transaction. Before starting its repeatable-read snapshot it takes fixed global DML-exclusion locks. It then proves current effective maintenance context/catalog and the existing bounded global malformed-tag condition. Historical invalidation receipts always deny apply/activation authority; they cannot replace these fresh observations. This path introduces no global all-entry audit or per-owner coverage ledger.

Under the volume-table exclusion lock it rejects any archive attached to the exact owner UUID, including foreign-tenant references hidden by ordinary RLS. It also rejects selected-owner foreign child rows. Only then does it switch that same transaction to a configured non-superuser, non-BYPASSRLS role and verify active RLS, rights and authenticated tenant context. Complete selected rows are reclassified and compared against the original owner/name/revision/dirty/projection. Table locks protect absent-row insertions and existing-row changes through commit. This is a globally exclusive maintenance operation, not an online ordinary tenant write.

A dirty equivalent row receives a parameterized dirty-only SQL update. The existing revision trigger advances its revision; updated_at is preserved. A clean equivalent row receives no update. The returned database token is published only when the outer transaction reports known commit. SQL/semantic refusals with acknowledged rollback return a bounded reason. Commit/rollback transport uncertainty returns unknown without a token, and poisons further apply on that instance.

`refreshUnknown(freshRootConnection)` requires a distinct root connection, the same active user, a settled prior invocation and a fresh current-maintenance exclusion barrier. It inspects current state under a newly qualified ordinary role and clears poison only after that fresh transaction completes known. It does not prove whether the old attempt committed, issue a historical success token or automatically replay. Failure, lock refusal or unknown refresh preserves poison. Callback completion alone is not backend commit completion.

The first apply slice additionally limits numeric YAML/JSON authority to finite safe integers. YAML floating-point scalars (including mathematically integral `9.0`) and PostgreSQL JSON numeric lexemes containing decimal/exponent notation are ineligible. Numeric-looking quoted strings remain strings. The existing size-, content-, schema- and expanded-structure-validated SecureYamlParser facade enforces the optional CORE numeric policy with typed YAML_NUMERIC_PRECISION refusal; original PostgreSQL row JSON text enforces the database side before a proposal/digest grants any equivalence eligibility; JavaScript-number equality alone is insufficient. This conservative apply-only restriction leaves the public read-only inspector unchanged and avoids silently accepting rounded values.

Selected projection limits retain the inspector's 10,000-row limits, 8 MiB raw UTF-8 prefetch, 2 MiB metadata/description, 16 MiB child/tag projections and 2 Mi UTF-16-unit legacy raw limit. Complete fingerprint data receives additional parent/tag byte bounds before transfer. Current global maintenance census retains its selected owner/tag/byte bounds. Lock and statement limits are 1 and 5 seconds; an invocation's checked deadline is 30 seconds. No automatic retry or timeout race abandons an undrained mutation.

Maintenance execution requires a separately reviewed plan keeping privileged role membership, session setup and relevant DDL stable. Locks and catalog observations do not defend against a superuser disabling triggers or replacing security policy outside that plan. Global privileged diagnostics expose only bounded refusal codes/counts, not private payloads.

The new integration tests use only the existing required CI PostgreSQL 17 service, uniquely owned databases/roles and exact-resource cleanup. Local qualification does not create or connect to a database. Real PostgreSQL results remain pending until that required CI runs; unit transaction adapters do not prove PostgreSQL commit behavior.
